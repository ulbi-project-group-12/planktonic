<domain>
## Phase Boundary

Turn the Phase 1 placeholders into real skeletons:
- `apps/web`: Next.js 16 with FSD, shadcn `shared/ui`, Vitest + RTL, Steiger, Storybook.
- `apps/api`: NestJS 12 ESM with config, health and Prisma 7 + adapter-pg, a first migration and Vitest.
- A dev `docker compose` with Postgres 18 + pgvector, Redis 8 and SeaweedFS.
- A CodeRabbit config.
- A README that takes a newcomer from clone to running in ≤ 30 min.

Out of scope: any product feature (auth, chat, realtime), prod compose (Phase 4), Orval/MSW (UL-24).
</domain>

<decisions>
## Implementation Decisions

### Scope (lead, 2026-11-12: "complete phase 1.1 completely")
- **D-01** UL-6, UL-7, UL-8, UL-10, UL-11 and UL-12 are all done in full by agents. The tickets' "learning mode" note is overridden by the lead.
- **D-02** UL-3 (kickoff, team agreements) is organisational. It is not done in code, and no plan contains it. Success criterion 5 stays a lead/human item in VERIFICATION.
- **D-03** One phase branch `gsd/phase-1.1-app-skeletons` and one PR to `main`. Its title carries the UL keys. Squash merge happens only after the lead's yes.

### Supply chain (Phase 1 rules, non-negotiable)
- **D-04** Every new dependency goes into the `catalog:` in `pnpm-workspace.yaml` with an exact version. Workspace manifests use `catalog:`, and `pnpm check:pins` must pass.
- **D-05** Versions are taken from STACK §15 and must be ≥ 14 days old (`minimumReleaseAge` 20160 enforces this, transitive deps included). If a §15 pin fails the age gate or the peer rules, pick the newest version that passes, record why, and never use `^`/`~`/`latest`.
- **D-06** Install scripts (prisma, @prisma/engines, esbuild, sharp, @swc/core, and anything else that needs them): use the pnpm 12 mechanism for approving builds (`allowBuilds` / `onlyBuiltDependencies`, whichever pnpm 12.15 actually reads — verify). The new top-level key in `pnpm-workspace.yaml` must first be added to the allowlist in `scripts/check-pins.mjs`, with a test in `scripts/check-pins.test.mjs`. This file is lead-owned (CODEOWNERS), and the lead runs this phase.
- **D-07** Never name the product in code or config. Use `@app/config/product`, otherwise `pnpm check:name` fails. READMEs are allowlisted.

### UL-8 docker-compose
- **D-08** The file is `compose.yaml` at the repo root, for dev only, with exact image tags (no `latest`):
  - `pgvector/pgvector:0.8.x-pg18`: verify the exact tag on Docker Hub;
  - `redis:8.10.3` (or the exact matching tag);
  - SeaweedFS `chrislusf/seaweedfs:4.52`, running a single-container `server -s3`.
- **D-09** SeaweedFS is chosen over Garage, with the reason recorded in a compose comment and the README. It is Apache-2.0, has a single-container S3 mode and is the first option in STACK §0/§9.
- **D-10** Every service has a healthcheck.
  - A one-shot init service (e.g. an aws-cli or `weed shell` based job) creates the dev bucket after S3 is healthy.
  - A Postgres init SQL in `/docker-entrypoint-initdb.d` runs `CREATE EXTENSION IF NOT EXISTS vector`.
  - Dev credentials are obviously-dev values supplied through env with defaults from `.env.example`. No real secrets.
  - Host ports are configurable via env, and the defaults should avoid common clashes (e.g. 5432 → configurable).

### UL-7 api
- **D-11** Follow STACK §3 and §3.1:
  - layout `src/core/`, `src/modules/`, `prisma/`;
  - the generated client goes in `src/generated/prisma` (gitignored, and generated in `build`/`typecheck` via a turbo dependency or a `prisma generate` script);
  - `PrismaService` lives in `src/core/prisma`.
  The `nest()` ESLint preset (packages/config) must pass with `--max-warnings=0`.
- **D-12** `GET /api/health` uses `@nestjs/terminus` with a global prefix `api`. Liveness works without a DB. Also add a DB readiness check that uses Prisma; the planner decides whether it lives in `/api/health` or `/api/health/ready`. Record the choice, because Phase 4 smoke-checks `/health`.
- **D-13** Use `@nestjs/config` with zod-validated env (zod is already in the catalog). `nestjs-zod` is incompatible with Nest 12, so do not use it.
- **D-14** Prisma 7.10.1 + `@prisma/adapter-pg` + `pg` 8.23.1, with `prisma.config.ts` holding the datasource URL. The first migration creates a minimal table, or an empty init migration plus `vector` already handled by compose; the planner decides, but `prisma migrate dev` must run against compose Postgres.
- **D-15** Tests use Vitest, ESM. Unit-test the health controller and service; an e2e test that boots the app is optional unless it is cheap. CI has no Postgres, so `pnpm test` must not need a DB.
- **D-16** The existing `apps/api/Dockerfile` and `release.yml` must still build. Adapt the Dockerfile if the build output changes.

### UL-6 web
- **D-17** Next.js 16.4.5 App Router per STACK §3.2:
  - the root `app/` is routing only and re-exports from `src/_pages`;
  - FSD layers in `src/`: `_app`, `_pages`, `widgets`, `features`, `entities`, `shared`;
  - shadcn (CLI 4.23.0 config + copied sources) in `src/shared/ui` with a public `index.ts`;
  - tailwindcss 4.3.5;
  - no `packages/ui`.
- **D-18** Tests use Vitest + @testing-library/react 16.3.3 + jsdom (or happy-dom), with a first test for a shared/ui component or the home page.
- **D-19** Steiger 0.9.0 + `@feature-sliced/steiger-plugin` 0.8.2 (exact pins), run as `steiger ./src` through a package script (`lint:fsd` or inside `lint`). Add a CI job `steiger` in `.github/workflows/ci.yml`. Prove it fails on a deliberate cross-feature import, then remove the probe.
- **D-20** The existing `apps/web/Dockerfile` must still build, using Next standalone output.

### UL-12 Storybook
- **D-21** storybook + `@storybook/nextjs-vite` 10.6.6.
  - Stories for Button, Input and Dialog cover their main states (default, disabled, error/invalid, Dialog opened).
  - Tailwind globals are loaded in preview.
  - `pnpm --filter web build-storybook` runs as a CI job.
  - Steiger must accept the `*.stories.tsx` placement.

### UL-10 CodeRabbit
- **D-22** Add `.coderabbit.yaml`:
  - review language `ru-RU` (team chat is Russian);
  - path filters exclude `pnpm-lock.yaml`, generated code (`**/generated/**`) and `.planning/**`;
  - profile chill;
  - no auto-approve.
  Installing the GitHub App on the org is a lead/org-owner action. The phase PR itself is the test PR.

### UL-11 README
- **D-23** Update the root `README.md` "Quick start" so it runs from zero: Node/pnpm versions, `cp .env.example .env`, `docker compose up -d`, migrate, `pnpm dev`.
  - Document every `.env.example` variable: purpose and a local example value.
  - Add a "Troubleshooting" section: port busy, Docker not running, wrong Node.
  - Update `apps/web/README.md` and `apps/api/README.md`.
  - Root `pnpm dev` runs web and api through turbo (`dev` task, persistent, no cache).
  - The two-member, two-OS walkthrough is a human UAT item.

### CI
- **D-24** `.github/workflows/ci.yml`: add the `steiger` and `storybook` jobs, reusing `.github/actions/setup`. Keep the actions SHA-pinned (the repo requires SHA pinning). Required-check registration in rulesets (`.github/rulesets/main.json`) gets updated for the new job names.
- **D-25** `pnpm check:all` must be green locally before the PR. `--max-warnings=0` applies everywhere.

### Claude's Discretion

- Which test environment the web tests use (jsdom vs happy-dom).
