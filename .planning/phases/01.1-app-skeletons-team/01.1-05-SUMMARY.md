# Phase 1.1 Plan 05: Prisma 7 + readiness for the api (UL-7, second half) Summary

**The api now runs Prisma 7.10.1 on the PrismaPg adapter. The `init` migration (`CREATE EXTENSION IF NOT EXISTS vector`) applies to compose Postgres through both `migrate deploy` and `migrate dev`. `GET /api/health/ready` returns 200 or 503 depending on the database, and `GET /api/health` stays database-free. All 18 tests, including an app-level e2e, run with no database.**

## Decisions (Claude's discretion, D-12/D-14)

- **Readiness endpoint:** `GET /api/health/ready` (terminus + `PrismaHealthIndicator`, `SELECT 1`) answers 503 with the body `{"status":"error",…,"database":{"message":"database unreachable","status":"down"}}`. `GET /api/health` stays liveness. Phase 4 smoke-checks `/api/health` on each replica and may gate traffic on `/ready`.
- **First migration:** no product table. `20261112211458_init/migration.sql` holds `CREATE EXTENSION IF NOT EXISTS vector;`, and Prisma generates a client from a schema with no models.
- **How SC2 is read (orchestrator, 2026-11-12):** "`GET /api/health` returns 200 under docker-compose" is the dev setup. In Task 1, `node apps/api/dist/main.js` on the host ran against compose Postgres, and `/api/health` and `/api/health/ready` both returned 200. `compose.yaml` has no api or web service: Task 3 checked that the service list is exactly `postgres redis s3-init seaweedfs`. Task 3's container on `app-verify_default` was an extra image check (D-16), not the SC2 evidence.

## Accomplishments

- `prisma/schema.prisma`:
  - generator `prisma-client` → `../src/generated/prisma`, with `moduleFormat esm`, `importFileExtension js` and `runtime nodejs`;
  - datasource `postgresql` with no URL;
  - no models.
- `prisma.config.ts`:
  - the URL is `datasource.url: process.env.DATABASE_URL`. No `env()` is used, and the URL is typed `url?: string`, so no `?? ''` was needed;
  - `process.loadEnvFile('<repo>/.env')` runs only when the argv holds `migrate`, `db` or `studio`, DATABASE_URL is unset and the file exists. `prisma generate` never loads it.
- `apps/api/turbo.json`:
  - the `generate` task has inputs `prisma/**`, `prisma.config.ts` and `package.json`, outputs `src/generated/prisma/**`, and `passThroughEnv: ["DATABASE_URL"]`;
  - `build`, `typecheck`, `lint` and `test` each use `dependsOn: ["$TURBO_EXTENDS$", "generate"]`.
- `.gitignore` gains `apps/api/src/generated/`.
- `PrismaService extends PrismaClient`:
  - it builds `new PrismaPg({ connectionString, connectionTimeoutMillis: 5000 })` from `ConfigService<Env, true>`;
  - it never calls `$connect`;
  - `onModuleDestroy` runs `$disconnect`.
- `PrismaHealthIndicator`:
  - it uses `HealthIndicatorService.check(key)`;
  - success returns `up()`;
  - any error returns `down({ message: 'database unreachable' })`, with no driver text.
- The `@Global()` `PrismaModule` exports both classes, and `AppModule` imports it.
- `HealthService.ready()` uses a named import of `PrismaHealthIndicator`. `HealthController` adds `@Get('ready')` and imports nothing from `core/prisma`.
- Env: `DATABASE_URL` is a required `z.url({ protocol: /^postgres(ql)?$/ })`, and an empty value counts as unset.
- Tests: 18 in total.
  - env: 11;
  - HealthService: 3 (live; ready up; ready down → `ServiceUnavailableException`);
  - HealthController: 2;
  - e2e: 2. The whole `AppModule` boots against `postgresql://probe:probe@127.0.0.1:1/probe`, set in `vitest.config.ts` `test.env`. Liveness returns 200. Readiness returns 503, and the body contains no `probe:probe` and no `127.0.0.1:1`.
- Layering probe: `src/modules/health/probe.controller.ts` imported `PrismaService` and failed `nest()` with "Controllers and gateways are adapters (STACK §3.1)…" (two `no-restricted-imports` errors and one `no-restricted-syntax`). It was deleted and never committed.
- Dockerfile: `RUN pnpm --filter @app/api generate` now runs before `build`. A header note says the Prisma CLI stays a devDependency and that the Phase 4 migrate service decides how it ships.
