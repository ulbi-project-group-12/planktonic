## Summary

Scope: `git diff main...HEAD` on `gsd/phase-1.1-app-skeletons`, without `.planning/` and
`pnpm-lock.yaml`. No `.env` file was read. I checked library behaviour that the findings depend on
against the installed packages: `@nestjs/config` 12.0.1 `forRoot`, the terminus 12.1.0 error logger,
the Next 16.4.3 CLI defaults and type-check step. I also ran a throwaway compose project to check
the exit code of `docker compose wait`.

Overall the skeletons are in good shape. Here is what holds up:

- **Health endpoints.** No error text leaks: the readiness check returns a fixed message, and an
  e2e test checks that the body contains neither the credentials nor `host:port`.
- **Env errors.** Validation errors name the variable but never its value.
- **Compose ports.** All three bind to `127.0.0.1`.
- **Images.** Both run as `node` (uid 1000) with root-owned code. Only `.next/cache` is writable.
- **CI.** Every third-party action is pinned to a full SHA, and every job has `timeout-minutes`.
- **Turbo graph.** `generate` comes before api build, typecheck, lint and test. `typegen` comes
  before web lint and typecheck. `transit` invalidates the web build when `product.ts` changes.
- **ESM.** Relative imports end in `.js`, and the Prisma generator is set to `esm` with `js` import
  extensions.
- **`services:up`.** `docker compose wait` does propagate a non-zero exit code from `s3-init`
  (checked: a container that exited 3 made `wait` return rc=3), so `pnpm services:up` fails
  correctly.

I found no blockers. The main concerns:

1. **Docs vs code: the product name.** Several docs and comments say `PRODUCT_NAME` /
   `PRODUCT_SLUG` override the name in the apps. No app reads them, and the web image bakes the
   name in at build time (WR-01).
2. **Dev servers listen on every interface.** The api, `next dev` and Storybook listen on all
   network interfaces, not only loopback (WR-02).
3. **Env-file loading has gaps.**
   - The api resolves its env-file paths from the current working directory (WR-03).
   - The Prisma CLI has no test/production guard, so it can read the root `.env` there (WR-04).
4. **Postgres healthcheck races `initdb`.** It can report healthy while the init-time temporary
   server is still running (WR-05).
5. **Readiness failures leave no trace.** The cause is thrown away, so operators see only a fixed
   message (WR-06).
6. **CODEOWNERS gaps.** A peer-approved change to a package script or Vitest config can neuter
   a required check (WR-07).

Accepted items I did not flag:

- the 14-day fallback versions and older compose image tags;
- the D-29 node base exception;
- SC2034 in `main-push-guard.yml`;
- Steiger 0.8.1 missing cross-feature re-exports.

### WR-01: Docs say the apps read PRODUCT_NAME / PRODUCT_SLUG, but no code reads them, and the web image bakes the name in at build time

**File:** `README.md:218-220` (also `.env.example:14-17`, `apps/web/README.md:86-87`, `apps/web/Dockerfile:3`, `apps/api/Dockerfile:3`, `apps/api/src/main.ts:1-2`)
**Issue:**

What the docs and comments say:

- `README.md:219-220`: "Apps read the `PRODUCT_NAME` / `PRODUCT_SLUG` env vars, which only override
  those defaults".
- `.env.example:14-15`: "these variables only override them".
- `apps/web/README.md:86-87` and both Dockerfiles: "The product name reaches the image only
  through the `PRODUCT_NAME` build-arg".
- `main.ts:1-2`: the name "reaches the process only through PRODUCT_NAME".

What the code does:

- `git grep` finds no reader of either variable in `apps/` or `packages/`. The only references are
  `ENV` lines in the Dockerfiles and `release.yml` / `ci.yml`.
- The web app renders `PRODUCT_DISPLAY_NAME` from `packages/config/product.ts`
  (`root-layout.tsx:7`, `home-page.tsx:15`). `next build` compiles it into the static HTML and
  metadata. The runtime `ENV PRODUCT_NAME=$PRODUCT_NAME` (`apps/web/Dockerfile:28`) cannot change
  it.

The consequence: `release.yml:99/151` passes `vars.PRODUCT_NAME` as a build-arg. If someone sets
that repo variable expecting the UI to change, as the README and the "Renaming" checklist step 2
suggest, the shipped images still show the `product.ts` name.

Summary 01.1-11 recorded this and left the Phase 1 prose untouched, so it is still a shipped
contradiction.

**Fix:** Pick one of the two:

- **Make the docs true.**
  - `README.md:218-220`: "The single source of the name is `packages/config/product.ts` … The apps
    import it at build time; `PRODUCT_NAME` is passed to the images as an env var, but no app code
    reads it yet, and `PRODUCT_SLUG` is reserved."
  - Reword `.env.example:14-15`, `apps/web/README.md:86-87`, both Dockerfile headers and
    `main.ts:1-2` the same way. For example: "The product name comes from
    `@app/config/product`; the `PRODUCT_NAME` build-arg is exported for future runtime use."
- **Or make the code true.** Have a server-side reader prefer `process.env.PRODUCT_NAME` over the
  constant, and make the page dynamic, or pass the name in as a build-time env for `next build`.

### WR-02: The api, `next dev` and Storybook listen on every network interface

**File:** `apps/api/src/main.ts:15`, `apps/web/package.json:8`, `apps/web/package.json:16`
**Issue:**

- **api.** `app.listen(port)` with no host binds `::` (every interface, dual-stack).
- **`next dev`.** Next's default is `0.0.0.0`. This is the installed 16.4.3 CLI's own help text:
  "Specify a hostname … (default: 0.0.0.0)".
- **Storybook.** `storybook dev -p 6006` has no `--host`, so it listens on every interface too.

The phase locks the compose services to `127.0.0.1` (D-10; `compose.yaml:8-9`, README "Local
services"). The dev processes that sit in front of them are open to the LAN, though. Today the api
only serves health endpoints. But once auth, chat and files land, every developer running
`pnpm dev` on café or office Wi-Fi exposes a dev api (with a dev database behind it) and a Next dev
server to the network.

**Fix:**

```ts
// env.ts: add a host with a loopback default
API_HOST: z.preprocess(emptyAsUnset, z.string().default('127.0.0.1')),
// main.ts
await app.listen(port, config.get('API_HOST', { infer: true }));
```

```dockerfile
# apps/api/Dockerfile runtime stage: the container must still listen on every interface
ENV API_HOST=0.0.0.0
```

```json
"dev": "next dev -H 127.0.0.1",
"storybook": "storybook dev -p 6006 --host 127.0.0.1 --ci"
```

Add `API_HOST` to `.env.example` and the README env table. The web image already sets
`HOSTNAME=0.0.0.0` for the standalone server, so it is not affected.

### WR-03: The api resolves its env-file paths from the current directory, and a package `.env` silently shadows the root one

**File:** `apps/api/src/app.module.ts:14`
**Issue:**

- **Paths depend on the working directory.** `envFilePath: ['.env', '../../.env']` is handed to
  `fs.existsSync` / `readFileSync` as is. `@nestjs/config` resolves array entries against the
  current directory (`config.module.js:39-41,150-154`). The paths are right only when the working
  directory is `apps/api`. Started from the repo root (`node apps/api/dist/main.js`, an IDE launch
  config, a debugger), the api loads the root `.env`, then a `.env` two directories above the
  checkout, outside the repository.
- **The app and the Prisma CLI can see different files.** `apps/api/.env` comes first, so it wins
  over the root `.env` for the app. `prisma.config.ts:15` only ever reads the root `.env`. A
  developer who adds `apps/api/.env` (`apps/api/README.md:50-51` invites it) can end up with the
  api and `pnpm db:migrate` on two different databases.

**Fix:** Anchor the paths to the module file, and keep the app and the CLI on one file:

```ts
import { fileURLToPath } from 'node:url';
// src/app.module.ts and dist/app.module.js are both one level below apps/api
const rootEnv = fileURLToPath(new URL('../../../.env', import.meta.url));
// …
envFilePath: [rootEnv],
```

Drop the per-package `.env` from `apps/api/README.md:50-51`. If you keep it, have
`prisma.config.ts` read the same list in the same order.

### WR-04: prisma.config.ts reads the root `.env` even when NODE_ENV is production or test

**File:** `apps/api/prisma.config.ts:17-23`
**Issue:** The phase rule is that `.env` is never read in test or production. The api enforces it
(`app.module.ts:18`), but the Prisma CLI config only checks for:

- `DATABASE_URL` being unset;
- a `migrate` / `db` / `studio` argument;
- the file existing.

So `NODE_ENV=production pnpm db:migrate` run from a checkout silently loads the developer or server
`.env` and runs `prisma migrate deploy` against whatever database it names. That could be:

- a Phase 4 one-shot migrate step run from a checkout;
- an operator on the server;
- a CI job that forgot to export `DATABASE_URL`.

This is the most dangerous command in the package, and it is the one that skips the guard.

**Fix:**

```ts
const mayReadDotEnv =
  process.env.NODE_ENV !== 'production' &&
  process.env.NODE_ENV !== 'test' &&
  process.env.CI === undefined;
if (
  mayReadDotEnv &&
  process.env.DATABASE_URL === undefined &&
  process.argv.some((arg) => DATABASE_COMMANDS.has(arg)) &&
  existsSync(rootEnvFile)
) {
  process.loadEnvFile(rootEnvFile);
}
```

Update the comment at lines 7-9 and `apps/api/README.md:59-61` to match.

### WR-05: The Postgres healthcheck can pass during initdb, before the real server is up

**File:** `compose.yaml:30`
**Issue:** On a fresh volume, the postgres entrypoint first starts a temporary server with
`listen_addresses=''` (unix socket only). That server runs the scripts in
`/docker-entrypoint-initdb.d`, then stops, and only then does the real server start.

`pg_isready` without `-h` checks the unix socket, so it reports "accepting connections" against
the temporary server. One success during the 10 s `start_period` marks the container healthy, so
`depends_on: service_healthy` and `docker compose wait s3-init` can go green while Postgres is
about to restart. A following `pnpm db:migrate` then hits a refused connection.

Today the window is small, because `seaweedfs` takes longer to get healthy. But the README promises
`services:up` returns only when Postgres is ready, and the Phase 4 production compose will likely
copy this healthcheck. There, an api or migrate service that depends only on postgres will race.

**Fix:** Probe over TCP, which the temporary server does not open:

```yaml
test: ['CMD-SHELL', 'pg_isready -h 127.0.0.1 -p 5432 -U "$${POSTGRES_USER}" -d "$${POSTGRES_DB}"']
```

### WR-06: The readiness indicator discards the error, so a 503 has no diagnosable cause anywhere

**File:** `apps/api/src/core/prisma/prisma.health.ts:18-21`
**Issue:** The bare `catch {}` replaces every failure with `'database unreachable'`, and nothing is
logged. Terminus logs only the details it was given (`health-check.service.js:54-55`), which here
is the same fixed string.

Keeping the HTTP body free of driver text is right. But the result is that operators cannot tell
apart:

- a wrong password (`28P01`);
- a missing database (`3D000`);
- `ECONNREFUSED`;
- a TLS error;
- a 5 s connect timeout.

None of these show in the response or in the logs. The Phase 4 smoke and load-balancer gating will
fail with no trail.

**Fix:** Log a value-free classifier on the server side and keep the HTTP body fixed:

```ts
private readonly logger = new Logger(PrismaHealthIndicator.name);
// …
} catch (error) {
  const code =
    (error as { code?: unknown }).code ?? (error instanceof Error ? error.name : 'unknown');
  this.logger.warn(`database readiness failed: ${String(code)}`);
  return session.down({ message: 'database unreachable' });
}
```

### WR-07: CODEOWNERS protects steiger.config.ts and turbo.json but not the scripts and configs that run the required checks

**File:** `.github/CODEOWNERS:33-38`
**Issue:** The comment's reasoning is that an app's Steiger config can switch off FSD rules and its
`turbo.json` can skip dependencies, so those files need lead review. The same bypass is open
through files that any teammate can change with a single peer approval:

- **`apps/web/package.json`.**
  - `"lint:fsd": "steiger ./src || true"` turns the required `steiger` check green.
  - `"build-storybook": "true"` does the same for `storybook`.
  - Dropping `--max-warnings=0` from `lint` weakens the `lint` check.
- **`apps/*/vitest.config.ts`.** Narrowing `include` turns `test` into a no-op.
- **`apps/web/.storybook/main.ts`.** Changing the `stories` glob does the same to `storybook`.
- **`apps/*/tsconfig.json`.** Turning off `strict` weakens `typecheck`.

The required checks still report success in every case.

**Fix:** Extend the lead-owned block:

```
/apps/*/package.json      @soadap
/apps/*/vitest.config.ts  @soadap
/apps/*/tsconfig*.json    @soadap
/apps/*/.storybook/       @soadap
```

A dependency change already needs the lead-owned `pnpm-lock.yaml`, so owning `package.json` adds
little review load.

## Info

### IN-01: The s3-init bucket check uses the bucket name as an unescaped regex

**File:** `compose.yaml:97-98`
**Issue:** `grep -Eq "^[[:space:]]*${S3_BUCKET}([[:space:]]|$)"` treats `.` (valid in S3 bucket
names) as "any character". With `S3_BUCKET=app.dev`, an existing `app-dev` or `appXdev` counts as
"already exists", the create is skipped, and the post-check passes too.
**Fix:** Compare the first field literally:
`… | awk '{print $1}' | grep -Fxq "$${S3_BUCKET}"`.

### IN-02: The readiness query has no query or statement timeout

**File:** `apps/api/src/core/prisma/prisma.service.ts:18-22`
**Issue:** `connectionTimeoutMillis: 5000` bounds only the connect. If a stalled database accepts
the connection but never answers `SELECT 1`, `/api/health/ready` hangs until the client or load
balancer gives up. The comment's promise ("fails readiness in seconds") does not hold.
**Fix:** Add `query_timeout: 5000` (client side) and/or `statement_timeout: 5000` to the
`PrismaPg` options, or race the probe against a timer in `PrismaHealthIndicator`.

### IN-03: check-pins accepts quoted `'true'` / `'false'` in allowBuilds

**File:** `scripts/check-pins.mjs:140`, `scripts/check-pins.mjs:217`
**Issue:** `mappingEntry` unquotes the value, so `esbuild: 'false'` passes as if it were the
boolean `false`. In YAML, `'false'` is a string, and a string `'false'` is truthy in JS. The guard
promises "every approval or denial is an explicit, reviewed line", but what the reviewer reads and
what pnpm receives can differ.
**Fix:** Reject quoted values for `allowBuilds`: check the raw `m[2]` against `/^(true|false)$/`
before unquoting, and add a test.

### IN-04: The web Dockerfile comment says the image runs no typecheck, but `next build` runs one

**File:** `apps/web/Dockerfile:21`, `apps/web/turbo.json:15-17`
**Issue:**

- Next 16.4.3 still type-checks during `next build` (`dist/build/type-check.js`, gated only by
  `typescript.ignoreBuildErrors`). The comment "lint and typecheck run in CI through Turbo, not in
  the image" is therefore wrong.
- For the same reason, the web `build` task's dependency on `typecheck` runs `tsc` twice on every
  CI build.

**Fix:** Correct the comment. Optionally set `typescript: { ignoreBuildErrors: true }` in
`next.config.ts`, since Turbo's `typecheck` already gates `build`. Alternatively, drop `typecheck`
from the build's `dependsOn`.

### IN-05: The README contradicts itself on visibility and Actions billing

**File:** `README.md:311-312`, `README.md:334-335`
**Issue:** Line 311 says the repository is public, and lines 334-335 (edited in this phase) say
every CI run bills the 7 required jobs against the free allowance. Standard runners are free for
public repositories. `.claude/CLAUDE.md` also says the repository is private for now.
**Fix:** State the current visibility once and make the billing sentence follow from it.

### IN-06: The env spec checks for value leaks with a single character

**File:** `apps/api/src/core/config/env.spec.ts:38-45`
**Issue:** `expect(message).not.toContain('0')` for `API_PORT=0` is a one-character substring
check. It passes or fails depending on zod's wording (any `>=10` or `0-65535` in a future zod
message breaks it) rather than on a leak.
**Fix:** Use values that cannot appear in a rule message (`'-12345'`, `'99999x'`), or assert on the
whole message, e.g. `toBe('Invalid environment: API_PORT: …')`.

### IN-07: Generality without instantiation: `passThroughEnv: ["DATABASE_URL"]` on the `generate` task

**File:** `apps/api/turbo.json:8`
**Category:** necessity
**Issue:** `generate` never needs a database URL:

- `prisma.config.ts:3-5` says `prisma generate` runs "without a database or a URL";
- `apps/api/Dockerfile:24` says "No DATABASE_URL is needed for it";
- CI runs `generate` with no `DATABASE_URL` exported.

The pass-through only lets a developer's URL leak into a task whose hash ignores it. Whether
`prisma generate` never consumes `datasource.url` when it is present rests on Prisma internals,
hence Info.
**Fix:** Remove `passThroughEnv` from the `generate` task.

### IN-08: Already defended elsewhere: the compose init SQL duplicates the init migration

**File:** `docker/postgres/initdb/01-extensions.sql:4`
**Category:** necessity
**Issue:** `prisma/migrations/20261112211458_init/migration.sql:3` runs the same
`CREATE EXTENSION IF NOT EXISTS vector`. The quick start (`README.md:37-38`) always runs
`pnpm db:migrate` before anything uses the database. `prisma migrate dev` also applies the
migration to its shadow database. Whether anyone uses the compose database without migrating is
a judgment call, hence Info.
**Fix:** Keep one source of truth. Either drop the initdb mount, or keep it and say in the comment
that it exists only for non-migrated ad-hoc use.
