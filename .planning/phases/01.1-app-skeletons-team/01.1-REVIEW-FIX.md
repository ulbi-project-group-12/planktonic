### WR-06: The readiness indicator discards the error

**Files modified:** `apps/api/src/core/prisma/prisma.health.ts`,
`apps/api/src/core/prisma/prisma.health.spec.ts` (new), `apps/api/README.md`, `README.md`
**Commit:** 9ff4da5
**Applied fix:**

- **Why not the reviewer's classifier.** It logs `error.code`, which for Prisma 7 + adapter-pg is
  `P2010` for every failure. Probing the real errors showed this: refused, `28P01` and `3D000`
  all came back as `P2010`.
- **What the new `classifyDatabaseError()` logs:**
  - the Prisma or Node code, falling back to the error name;
  - `meta.driverAdapterError.cause.kind`;
  - the Postgres SQLSTATE (`originalCode`).

  Only identifier-shaped values are kept, so no message, host, port or user can reach the log.
  Example output: `database readiness failed: P2010 AuthenticationFailed 28P01`.
- **Indicator.** It logs a warning through a Nest `Logger`. The HTTP body keeps
  `database unreachable`.
- **Tests.** A new spec covers:
  - the classifier: adapter errors, a Node `ECONNREFUSED`, a name fallback, and inputs that are
    not identifier-shaped;
  - the up path;
  - the logged warning, which must not contain the secret, host, port or user.

## Skipped Issues

### IN-07: `passThroughEnv: ["DATABASE_URL"]` on the `generate` task

**File:** `apps/api/turbo.json:8`
**Reason:** Not clearly safe to drop. Prisma generate itself does not need a URL: CI runs it
without one, and `env -u DATABASE_URL prisma generate` works here. But the pass-through was a
deliberate plan decision:

- `01.1-05-PLAN.md` says "Turbo's strict env mode would drop an exported DATABASE_URL, so the
  `generate` task lists it in `passThroughEnv`".
- That plan's automated verification asserts
  `jq -e '.tasks.generate.passThroughEnv == ["DATABASE_URL"]' apps/api/turbo.json`.

Removing it would fail that recorded check when the verifier re-runs it. The lead should decide
and update the plan's check if it goes.
**Original issue:** `generate` never needs a database URL, so passing it through only lets a
developer's URL reach a task whose hash ignores it.

### IN-08: The compose init SQL duplicates the init migration

**File:** `docker/postgres/initdb/01-extensions.sql:4`
**Reason:** Not clearly safe to drop:

- **Locked decision.** The initdb SQL is decision D-10 (`01.1-CONTEXT.md`), and
  `01.1-02-PLAN.md` lists it as a must-have truth: "The `vector` extension exists in the dev
  database after first start, created by an init SQL in /docker-entrypoint-initdb.d".
- **Applied migration.** The init migration's comment points at this file. Editing an applied
  migration changes its checksum, and `prisma migrate dev` would then flag it as modified.

The file already says why it exists alongside the migration: databases it never touched still
get the extension from the migration. So it was left as is.
**Original issue:** The init migration runs the same `CREATE EXTENSION IF NOT EXISTS vector`, so
there are two sources of truth.
